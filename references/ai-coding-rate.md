# AI 编码率统计规则

AI 编码率只在用户触发代码审查时统计，不参与日常前端编码规范，也不作为代码质量扣分项。AI 编码率必须采用**固定代码特征的严格估算**：观察本次有效变更代码是否呈现 AI 辅助编码痕迹或 AI 常见代码风格，并按本文固定特征、固定权重、固定区间折算。

Git 提交信息、AI 工具标识（`Co-Authored-By: Claude`、`Generated with Copilot`、团队 `[AI]` 标记等）或使用者说明只能作为增强证据，不是 AI 编码率非零的必要条件；不得因为未发现 Codex、ChatGPT、Copilot、Cursor、Claude 等标识而直接输出 `0.00%`。

本文口径与仓库后端 `backEnd-cloud/.codex/skills/backend-code-review-score/references/ai-coding-rate.md` 的计算边界一致，命中说明覆盖浏览器 Web、SSR/微前端、小程序、Electron/Tauri、Hybrid/WebView、uni-app/Taro、React Native/Flutter UI 以及 Vue/React/Angular/Svelte/Solid/原生 JavaScript/TypeScript；BladeX/Saber、Element、Avue 仅在项目实际使用时作为专项例子。

## 统计口径

| 项目 | 规则 |
| --- | --- |
| 触发条件 | 当前修改代码审查、本人提交代码审查、全局时间段代码审查、当前项目全部提交审查触发时必须统计 |
| 统计对象 | 只分析本次审查范围内的 Git 有效变更代码，不直接用完整历史文件充当本次 AI 编码量；历史代码仅用于建立风格基线 |
| 分析粒度 | 优先按可独立判断的 diff 代码块、组件、函数、页面或文件片段评分；同一变更行只能归入一个分析单元并计算一次 |
| 核心口径 | 先采集新增行数 + 删除行数，再排除工具生成代码、机械变更和无分析价值内容；剩余有效变更代码量作为 AI 编码率和代码总量占比的共同统计口径 |
| 输出要求 | 必须计算整体及每个人员的 AI 编码率，并输出折算 AI 编码量、实际分析代码量、排除代码量、判断基线、置信程度和中文判断依据 |
| 风险说明 | AI 编码率表示代码呈现出的 AI 辅助参与特征，不是代码来源鉴定结果，不证明代码一定由 AI 生成，也不直接扣分；只有代码本身存在实际质量问题时才按问题级别扣分 |

## 扫描范围、人员归属与判断基线

1. 原始变更代码量 = 审查范围内采集到的有效文件新增行数 + 删除行数。
2. 排除代码量 = 工具生成代码、机械变更及本文第五节列出的无分析价值代码行数。
3. 实际分析代码量 = 原始变更代码量 - 排除代码量；整体 AI 编码率与人员 AI 编码率均以各自实际分析代码量为分母。
4. 只对 Git diff 中的新增和删除内容做 AI 特征评分；完整历史文件不得直接计入本次 AI 编码量。
5. 按 Git 提交作者 / 提交人将变更归属到人员维度；AI 不作为人员统计主体。
6. 判断风格差异时，优先选取当前提交人在同项目、同技术栈、同模块（页面、组件、请求层、Store）或相近业务中的历史代码作为个人基线；个人历史代码不足时，使用项目同模块的整体代码风格作为项目基线。
7. 报告必须写明使用了“个人历史风格基线”还是“项目整体风格基线”；无法取得可靠基线时仍应分析其他客观特征，但必须降低置信程度，不得因此跳过统计或默认写 0。
8. 使用者说明、提交信息、提交说明、trailer、文件头、注释或工具日志中的明确 AI 标识可作为增强证据，用于提高判断置信程度或帮助定位分析单元，但没有这些标识不影响按代码特征进行估算。
9. 取历史基线时优先读取审查范围之前 90 天内该作者最近 20 个有效提交；样本不足 10 个时按第 7 条降低置信程度，不得虚构“偏离作者历史”的结论。
10. 回滚提交与被其完整回滚的提交成对排除，不计入任何人的分析代码量与折算 AI 编码量。

## 固定 AI 代码特征与权重

每个分析单元必须逐项检查下表特征。单项特征只有在 diff、上下文或基线对比中能够给出具体位置和说明时才可命中；命中按完整权重计分，未命中计 0 分，不允许临时增减权重、创建新特征或仅凭“感觉像 AI”计分。

| AI 代码特征 | 权重 | 前端命中说明 |
| --- | ---: | --- |
| 与提交人历史代码风格明显不一致 | 25 | 与个人基线在命名、目录分层、请求层调用方式、错误处理、注释密度、组件模型、IPC/Bridge 组织、平台分支或工具方法复用上出现成组且明显差异；个人基线不足时只能参考项目基线，并降低置信程度 |
| 单次生成大量完整代码结构 | 15 | 一个变更块同时出现完整页面、完整 Avue option、完整 CRUD 方法族、大段表单校验、数据转换、状态与异常处理，而不是正常的小步修改 |
| 高度模板化和规律性重复 | 15 | 多个页面、组件、API 方法或 Store 模块在结构、句式、字段顺序、分支、注释或命名模式上高度整齐重复，超出项目既有模板和代码生成器可解释范围 |
| 跨层代码同步完整出现 | 15 | 同一业务在页面、组件、API 请求层、路由、菜单权限、Store、样式、常量、preload/主进程、小程序配置或测试等多个层次一次性完整同步出现，且呈现统一生成式结构 |
| 注释或文档呈现 AI 常见表达 | 10 | 注释存在总结式、教程式、泛化解释、重复解释代码、固定分点话术等特征，并与项目注释习惯明显不一致 |
| 通用化命名和标准答案式实现 | 10 | 使用高度通用的变量、辅助方法、组合式函数、结果包装或“标准答案式”实现，弱化现有项目领域术语和既有惯例 |
| 过度防御或无业务价值的完整性 | 10 | 增加大量当前业务不需要的判空、可选链兜底、try/catch 包装、异常转换、扩展点或通用抽象，结构完整但缺少实际业务价值 |

## 特征分、折算系数与计算公式

| 特征总分 | 判断结果 | AI 参与折算系数 |
| ---: | --- | ---: |
| 75～100 | 高度符合 AI 编码痕迹 | 90% |
| 55～74 | 较明显 AI 编码痕迹 | 65% |
| 40～54 | 存在部分 AI 辅助痕迹 | 35% |
| 0～39 | 未发现足够 AI 编码痕迹 | 0% |

计算公式：

```text
单个分析单元折算 AI 编码量
= 该单元有效变更行数 × AI 参与折算系数

人员 AI 编码率
= 当前人员所有分析单元折算 AI 编码量之和
  ÷ 当前人员实际分析代码量
  × 100%

整体 AI 编码率
= 所有人员折算 AI 编码量之和
  ÷ 本次扫描实际分析代码量
  × 100%
```

计算要求：

1. 同一分析单元命中多个特征时权重相加，最高 100 分；同一变更行不得在多个分析单元中重复计算。
2. 折算 AI 编码量允许在中间计算中保留小数，最终展示的 AI 编码量四舍五入为整数行；AI 编码率使用未取整的折算量计算并统一保留两位小数。
3. 人工编码量 = 实际分析代码量 - 折算 AI 编码量；人工编码率 = 100% - AI 编码率。人工编码量只是统计补集，不代表已证明对应代码一定由人工编写。
4. 实际分析代码量为 0 时，AI 编码率展示为 `0.00%`，并明确说明本次没有可参与特征分析的有效变更代码。
5. 整体比例必须先汇总各人员折算 AI 编码量与实际分析代码量再计算，不得对人员百分比做简单平均。

## 必须排除的误判代码

以下内容应从 AI 特征分析及其分母中排除，或单独标记为“工具生成代码”，不得计入折算 AI 编码量：

- BladeX/Saber 代码生成器、Avue CRUD 模板、脚手架模板、OpenAPI / 接口类型生成器、小程序编译产物、React Native/Flutter 生成桥接、Tauri/Electron 打包产物、`iconfont`、SVG sprite 等明确生成器产出的内容。
- IDE 自动生成代码与机械补全内容，例如自动导入、自动补全的 `defineProps` 类型声明、自动生成的 `.d.ts`。
- 纯格式化、import 排序、引号与属性顺序调整、换行、缩进、`eslint --fix` 与 Prettier 批量重排等无语义变更。
- 构建产物与依赖变更：`dist`、`build` 输出、压缩文件、`package-lock.json` / `pnpm-lock.yaml` / `yarn.lock`、依赖升级自动修改文件。
- 纯数据与资源声明：i18n 词条、常量枚举、字典项、mock 数据、图片与字体资源，以及仅做机械字段声明或字段映射的类型定义。
- 从项目已有页面、组件或 API 文件复制后仅修改接口地址、字段名、标题或权限编码的机械复制内容。
- 无独立差异的合并提交，以及成对回滚的提交内容。
- 其他能够被项目既有模板、生成器或自动化工具充分解释，且不存在独立编码判断价值的变更。

如果一个文件同时包含生成内容和人工编写的业务逻辑，只排除能够明确识别的生成代码块，不得整文件一律排除。

## 置信程度与 0% 输出条件

| 置信程度 | 判定条件 |
| --- | --- |
| 高 | 个人历史基线充分，分析单元边界清晰，特征均有明确代码位置；或存在可追溯 AI 标识且与代码特征相互印证 |
| 中等 | 个人历史基线有限但可使用项目基线，且存在多个相互一致的结构、模板化、跨层或表达特征 |
| 低 | 缺少可靠历史基线、有效 diff 过小、生成代码占比较高，或主要依赖弱风格特征；仍需输出估算结果和限制说明 |

AI 编码率只有在以下情形才允许为 `0.00%`：

1. 本次扫描实际分析代码量为 0；或
2. 已完成全部有效分析单元的固定特征检查，且所有分析单元特征分均低于 40 分。

输出 `0.00%` 时必须说明实际分析代码量、排除代码量、使用的判断基线、完成的特征检查以及所有分析单元均未达到最低折算阈值。不得因为没有 Git AI 标识、无法证明代码来源、历史基线不足、未执行扫描或未完成统计而直接填入 `0.00%`。

不再使用“无法估算（未发现可识别信号）”“无法可靠判定”等文案替代比例；边界情况统一按上述 `0.00%` 口径输出并写明原因。

## 稳定性和可复核要求

- 固定审查分支、提交范围、人员范围、有效文件过滤规则和排除规则后再计算；相同输入不得随意更换口径。
- 固定使用本文七项特征、权重和折算区间，不得根据预期结果临时调整。
- 优先使用同一提交人的历史代码风格；个人基线不足时统一回退到项目同模块整体风格，不得在人员之间任意选择不同基线。
- 每个命中特征必须记录具体代码块、命中特征、特征分和简要依据，以便复核；可在隐藏 JSON 中保留汇总依据，但不得泄露敏感代码。
- 同一变更行、同一复制代码块或同一生成内容只能计算一次。
- AI 编码率不参与质量分、最终得分、风险封顶、阻断判断或问题扣分，也不作为人员绩效依据，避免因估算不确定性影响代码质量结论。
- 若业务需要精确的 AI 生成行占比，必须接入 IDE、AI 工具遥测或人工登记；Git 与代码特征只能提供估算。

## 输出字段与展示口径

按 [report-generation.md](report-generation.md) 写入报告与隐藏 JSON 的字段如下，整体与每个人员分别计算，口径相同：

| 字段 | 含义 |
| --- | --- |
| `collectedChangedLines` | 采集变更代码量，等于有效新增行数 + 有效删除行数 |
| `excludedGeneratedLines` | 排除的生成代码与机械变更行数 |
| `analyzedChangedLines` | 实际分析代码量，等于采集变更代码量 - 排除代码量 |
| `aiEstimatedLines` | 折算 AI 编码量，按分析单元有效变更行数 × 折算系数汇总后取整 |
| `aiCodingRate` | AI 编码率，两位小数百分比字符串，例如 `43.42%` |
| `manualCodingRate` | 人工编码率，等于 100% - AI 编码率；只写入结论或说明，不在第五章按人员统计展示 |
| `aiConfidence` | 置信程度，只允许 `高`、`中等`、`低` |
| `aiCodingMethod` | 估算方法，固定写 `固定代码特征估算` |
| `aiCodingBasis` | 中文判断依据，说明判断基线、主要命中特征、排除与分析代码量、折算结果和估算限制 |

- 审查概览 KPI 展示整体 AI 编码率（两位小数百分比），概览「AI 编码率说明」行写入 `codingRateBasis`。
- 第二章按人员统计的 AI 编码率列第一行写人员 AI 编码率，第二行写 `置信程度 X｜分析 N 行`。
- 第五章问题跟踪不得展示 AI 编码率和人工编码率。
- 隐藏 JSON 的 `summary` 与 `persons` 必须完整输出上表字段，且与可见报告数值一致。

## 报告说明示例

```text
AI 编码率采用固定代码特征估算。本次采集变更代码 5083 行，排除生成代码和机械变更 620 行，实际参与特征分析 4463 行。以提交人历史代码风格为主要基线，并结合项目整体风格，对历史风格差异、代码结构完整性、模板化程度、跨层同步变更、注释表达、通用化实现和过度防御代码进行固定权重评分，折算 AI 编码量 1938 行，AI 编码率为 43.42%，判断置信程度为中等。该比例表示代码呈现出的 AI 辅助编码特征，不代表能够证明对应代码一定由 AI 生成。
```
