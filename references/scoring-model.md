## 评分总则

| 项目 | 规则 |
| --- | --- |
| 满分 | 100 分 |
| 计算方式 | 从各维度满分开始，按已确认问题扣分 |
| 最低分 | 单维度和总分均不低于 0 分 |
| 证据要求 | 每个扣分项必须能追溯到源码位置、提交或当前 diff、规则来源和验证证据 |
| 不确定问题 | 标记“待确认”，不扣分；列出需要补充的接口、权限、数据或环境证据 |
| 重复问题 | 同一根因合并计分，根据影响范围提高扣分，不对同一事实重复惩罚；具体按码表第四节 `rootCauseKey / locationFingerprint / descriptionNorm` 规则执行，保证重复扫描幂等 |
| 同人堆叠 | 同一人员的多个主要及以下问题按“同人堆叠递减”折算计入扣分，防止中低级别问题线性堆叠出比严重问题更坏的总分 |
| 纯格式问题 | 不扣分，记为 Info；若导致 lint、编译或运行失败，则按实际影响定级 |
| 基线失败 | 已存在且与本次审查对象无因果关系的构建、测试或运行失败不扣分，单列为历史基线或环境风险 |
| 阻断优先 | 一票阻断项独立于分数生效 |
| 风险封顶 | 先计算原始分，再取原始分与风险封顶分的较小值 |

总分公式：

```text
维度得分 = max(0, 维度满分 - 该维度计入扣分合计)
原始总分 = 所有维度得分之和
最终总分 = min(原始总分, 风险封顶分)
```

公式中的扣分均指按“同人堆叠递减”折算后的计入扣分；问题清单和问题详情仍展示每个问题的原始扣分。

## 评分维度

| 评分维度 | 分值 | 重点检查 |
| --- | ---: | --- |
| 功能契约与交互正确性 | 20 | 需求完整性、业务流程、表单校验、分页筛选、边界数据、异常恢复、重复提交、兼容行为 |
| 架构分层与复用边界 | 15 | 目录职责、依赖方向、现有请求/路由/权限/组件复用、重复实现、核心设施影响 |
| API、数据、权限与安全 | 15 | URL/method/params/data、响应层级、Token、租户、按钮权限、XSS、敏感信息、上传下载 |
| 组件、状态与生命周期 | 15 | 组件输入输出、响应式/Store、页面与窗口生命周期、watch/effect、副作用清理、IPC/Bridge 状态闭环、平台状态恢复 |
| UI、可访问性与兼容性 | 10 | 设计还原、布局滚动、浏览器/桌面/小程序视口、语义、键盘、焦点、触控、字体缩放、端间差异、空态和错误态 |
| 性能与资源使用 | 10 | 重复请求、渲染抖动、大列表、包体、懒加载、图片资源、事件/定时器泄漏、无界缓存 |
| 可维护性与规范一致性 | 10 | 命名、复杂度、重复代码、注释、死代码、调试代码、项目 ESLint/Prettier 和局部风格 |
| 测试与验证 | 5 | 定向测试、lint/typecheck/build、静态报告检查和回归范围 |
| 合计 | 100 | 从各维度满分开始扣分 |

维度只是问题归属，不改变严重级别扣分区间。一个问题跨多个维度时，选择主要根因所在维度，并在影响说明中列出次要影响，避免重复扣分。

## 问题级别与扣分

| 级别 | 定义 | 单个问题扣分 | 门禁 |
| --- | --- | ---: | --- |
| Blocker | 应用不可用、核心流程完全失败、确认的数据破坏、严重越权或可直接利用的高危漏洞 | 20-30 | 必须阻断 |
| Critical | 核心功能错误、确认的安全漏洞、全局基础设施回归、严重性能或稳定性风险 | 10-19 | 通常阻断 |
| Major | 重要局部功能、状态、架构、兼容或维护问题，影响真实用户或后续扩展 | 5-9 | 视场景阻断 |
| Minor | 局部质量问题，当前不破坏主流程，但会增加误用、维护或回归成本 | 1-4 | 一般不阻断 |
| Info | 建议优化或纯格式问题，没有可证明的当前风险 | 0 | 不阻断 |

### 级别中文映射与展示

| 英文枚举 | 中文展示 |
| --- | --- |
| Blocker | 阻断 |
| Critical | 严重 |
| Major | 主要 |
| Minor | 次要 |
| Info | 提示 |

- 报告、问题清单、问题详情和级别统计中，级别列必须显示中文；英文枚举仅用于内部计算和 `badge-*` 样式类。
- 上游数据出现英文级别时，渲染前必须完成映射，不得直接透出。
- HTML 模板必须在“问题清单”中使用可折叠表格完整展示五种中文级别、扣分区间、是否必须修复及含义；该表是固定模板内容，不使用动态占位符。

### 扣分取值

| 判定因素 | 低值 | 中值 | 高值 |
| --- | --- | --- | --- |
| 影响范围 | 单个局部且易修复 | 单页、单组件或单接口 | 跨页面、跨模块、全局基础设施或核心流程 |
| 可复现性 | 仅特定边界 | 常见条件可触发 | 默认路径稳定触发 |
| 用户影响 | 轻微体验或维护成本 | 操作失败、状态错误或局部数据错误 | 无法使用、敏感数据暴露或核心数据风险 |
| 修复成本 | 局部修改 | 需要联动调用方 | 需要架构、接口或多系统协同 |
| 证据强度 | 静态证据 | 测试或构建证据 | 源码、日志、测试和可复现链路相互印证 |

只有推测而无明确证据时不得通过“取区间低值”扣分，必须标记待确认。

### 同人堆叠递减

同一人员的多个主要（Major）和次要（Minor）问题往往共享同一修复上下文和回归范围，边际风险递减；线性累加会使一批主要问题扣出比严重问题更坏的总分，与真实风险不符。计入扣分按以下规则折算：

```text
计入扣分 = 原始扣分 * 递减系数
```

| 同人序号（按原始扣分降序） | 递减系数 |
| --- | ---: |
| 第 1 个 | 100% |
| 第 2 个 | 90% |
| 第 3 个 | 80% |
| 第 4 个 | 70% |
| 第 5 个 | 60% |
| 第 6 个及以后 | 50% |

- 只有主要和次要问题参与递减；阻断（Blocker）和严重（Critical）问题恒按原始扣分全值计入，也不占用递减序号。安全风险不因数量多而摊薄。
- 递减按人员独立执行：把该人员全部主要/次要问题按原始扣分从高到低排序后依次套用系数。
- 维度扣分、人员扣分、模块统计和级别统计一律使用计入扣分；各合计分别四舍五入到整数，允许合计之间出现 1 分以内的舍入差异。
- 问题清单和问题详情展示原始扣分，保持问题本身的定级口径不变；第五章统计表的扣分列使用递减后计入扣分合计。

### 功能契约与交互正确性

| 问题示例 | 默认级别 | 说明 |
| --- | --- | --- |
| 提交参数或字段映射错误，导致核心业务写入错误 | Critical/Blocker | 依据数据影响和是否可恢复定级 |
| 主流程按钮无效、路由打不开、表单永远无法提交 | Critical | 整个应用或核心入口失效可升为 Blocker |
| loading、Avue `done/loading`、弹窗状态在失败分支无法复位 | Major | 导致页面持续不可操作时取高值 |
| 搜索、分页、排序、空值或日期处理与接口契约不一致 | Major | 仅极端边界且影响轻微时可为 Minor |
| 危险操作缺少二次确认或重复提交保护 | Major/Critical | 可能造成不可逆数据影响时提高等级 |

### 架构分层与复用边界

| 问题示例 | 默认级别 | 说明 |
| --- | --- | --- |
| 新建第二套全局 axios、Token、路由或权限机制 | Major/Critical | 已破坏认证或全局行为时为 Critical |
| 普通业务页面直接修改入口、请求拦截器、权限守卫或全局状态 | Major/Critical | 根据全局回归证据定级 |
| 页面、API、option、组件或 Store 职责越界 | Major | 造成实际功能错误时按功能风险升级 |
| 未复用相邻模块已有工具，复制业务规则导致实现分叉 | Major | 仅小段无风险重复可为 Minor |
| 为统一风格整页重写历史 Options/Composition API | Major | 若只是无关 diff 且无回归可为 Minor |

平台边界补充判定：

| 问题示例 | 默认级别 | 说明 |
| --- | --- | --- |
| Electron/Tauri 渲染层绕过 preload 直接使用 Node 或任意 IPC | Critical | 形成可利用的主机能力越权时阻断 |
| 主进程、preload、渲染进程职责混杂或 IPC 通道无白名单 | Major | 影响多个窗口或敏感能力时可升级 |
| 小程序页面未按生命周期、分包或平台 API 约束实现 | Major | 造成页面失效、超包体或权限请求异常时可升级 |
| uni-app/Taro/React Native/Flutter 平台分支缺少能力探测与降级 | Major | 端间功能不一致或弱网不可恢复时取高值 |
| SSR/微前端共享状态、样式或依赖未隔离 | Major | 造成 hydration 错误或跨应用污染时可升级 |

### API、数据、权限与安全

| 问题示例 | 默认级别 | 说明 |
| --- | --- | --- |
| 仓库、前端包、日志或页面暴露真实 Token、密码、私钥 | Blocker | 必须删除并轮换凭据 |
| 可利用的 DOM/反射/存储型 XSS，或危险 HTML 未净化 | Critical/Blocker | 无需认证且影响广泛时可为 Blocker |
| URL、method、params/data、响应层级与已确认契约不一致 | Major/Critical | 核心写操作错误时为 Critical |
| 权限编码、菜单路径或请求选项由实现者猜测 | Major | 已造成越权或敏感操作暴露时升级 |
| 仅隐藏按钮并把它当作真实鉴权 | Major | 若已实测后端无鉴权且可越权则为 Critical/Blocker |
| 控制台、埋点或错误消息泄露完整认证信息、隐私或内部数据 | Critical/Major | 按敏感度和暴露范围取值 |
| 上传下载绕过项目鉴权、类型/大小限制或安全处理 | Major/Critical | 存在可利用路径时提高等级 |

### UI、可访问性与兼容性

| 问题示例 | 默认级别 | 说明 |
| --- | --- | --- |
| 目标桌面视口出现遮挡、裁剪、不可滚动或关键操作不可见 | Major/Critical | 核心操作完全不可达时为 Critical |

| 问题示例 | 默认级别 | 说明 |
| --- | --- | --- |

| 问题示例 | 默认级别 | 说明 |
| --- | --- | --- |

## 一票阻断与风险封顶

### 一票阻断

出现以下任一情况时，必须标记阻断：

- 存在 Blocker。
- 存在影响核心流程、敏感数据、认证权限或全局稳定性的 Critical。
- 本次改动导致目标应用无法构建、启动或完成基本路由加载。
- 核心用户流程在可复现条件下完全不可用，或写入错误可能破坏核心数据。
- 存在可利用的 XSS、明文密钥、确认越权、任意跳转到恶意来源等高风险安全问题。
- 用户明确要求必须修复的问题仍未处理。
- 核心链路证据不足以判断能否安全合并或发布，且缺口无法通过当前环境补齐。

### 风险封顶

触发多个条件时取最低上限：

| 风险情况 | 最终分数上限 |
| --- | ---: |
| 存在 Blocker | 49 |
| 存在 Critical 必须修复项 | 59 |
| 存在未修复的高风险安全漏洞 | 59；无需认证且可广泛利用时为 49 |
| 应用因本次审查对象而无法构建、启动或加载基本路由 | 49 |
| 核心业务流程因本次审查对象而无法完成 | 59；造成确认的数据破坏时为 49 |
| 修改入口、全局请求、路由、权限、核心状态或构建配置但未完成必要回归 | 69 |
| 任一有效参与人得分低于 50 | 64 |
| 任一有效参与人得分低于 60 | 69 |
| 超过 1/3 的有效参与人得分低于 70 | 74 |
| 超过 20% 的有效参与人得分低于 80 | 79 |
| 未触发任何封顶条件 | 100 |

风险封顶不是额外扣分。报告必须分别展示原始总分、风险封顶分、最终总分和封顶原因。

低分人员已经通过低分尾部得分（权重 25%）和最低人员得分（权重 20%）计入团队综合原始分，个人低分封顶只用于兜底极端情况，不得把单个人员的分数直接当作团队分数上限；否则同一低分事实会被三重惩罚。

## 评分等级

| 得分 | 等级 | 结论 |
| ---: | --- | --- |
| 90-100 | A | 质量优秀，可通过；仍需处理明确必须修复项 |
| 80-89 | B | 质量良好，可通过或带建议通过 |
| 70-79 | C | 存在明显风险，修复主要问题后复审 |
| 60-69 | D | 勉强达标，通常需要整改后复审 |
| 0-59 | E | 不通过，必须整改 |

等级不能覆盖阻断结论。即使最终得分达到 A/B，只要存在阻断项，门禁仍为不通过。

### 评分校准检查

- 当本次审查的最高问题级别为主要（Major）及以下时，团队最终得分通常应落在 65-85 区间；计算结果低于 60 时，必须复核同人堆叠递减是否执行、封顶条件与附加扣分是否重复惩罚同一事实、扣分取值是否系统性偏高，并在审查依据中说明复核结论。
- 校准检查不是加分项：不得因“版本已上线运行”直接上调分数；上线状态只能作为分数量级是否失真的旁证。
- 复核后分数仍低于区间时，保留计算结果，并在结论中说明主导原因（例如低分人员占比过高或存在集中安全风险）。

## 单人和团队算法

### 单人得分

```text
人员原始得分 = max(0, 100 - 该人员计入扣分合计)
人员最终得分 = min(人员原始得分, 该人员适用的风险封顶分)
```

计入扣分合计按“同人堆叠递减”折算：阻断和严重问题全值累加，主要和次要问题按降序套用递减系数后累加，再四舍五入到整数。

仅修改空行、纯格式、文档、生成文件且无业务影响的人员可列为“非有效参与人”，不纳入团队综合评分。回滚提交与被其完整回滚的提交成对排除；仅剩回滚对的人员按非有效参与人处理。

### 团队综合得分

简单平均分只作参考。团队结论使用短板风险校正算法：

```text
团队综合得分 = max(0, min(综合原始分, 团队风险封顶分))

综合原始分 = 0.55 * 加权平均分
           + 0.25 * 低分尾部得分
           + 0.20 * 最低人员得分
           - 严重问题附加扣分
```

### 贡献权重与代码总量占比

贡献权重只用于团队评分，不作为报告展示列；报告第二章展示的是与 AI 编码率共用分母的代码总量占比。

```text
原始贡献权重 = 0.50 * 代码行数权重
             + 0.30 * 文件数量权重
             + 0.20 * 提交次数权重

代码行数权重 = sqrt(该人员有效变更行数) / Σsqrt(所有人员有效变更行数)
文件数量权重 = sqrt(该人员有效变更文件数) / Σsqrt(所有人员有效变更文件数)
提交次数权重 = sqrt(该人员有效提交次数) / Σsqrt(所有人员有效提交次数)

代码总量占比 = 该人员实际分析代码量 / 本次扫描实际分析代码量
```

- 排除生成文件、压缩产物、纯格式化和无业务影响的锁文件后再计算贡献；回滚提交与被其完整回滚的提交成对排除，不计入任何人的贡献与占比。
- 有效变更行数、实际分析代码量按 [ai-coding-rate.md](ai-coding-rate.md) 的统一口径统计：有效新增行 + 有效删除行，再扣除生成代码与机械变更。
- 代码总量占比保留两位小数，各有效参与人合计 100%，写入报告第二章按人员提交统计，并与该人员 AI 编码率共用“实际分析代码量”分母；非有效参与人写“不计入”。
- 口径依据：贡献权重把行数、文件数、提交次数三个信号先开方缓和再加权，与任一单指标呈次线性关系，可抑制大段粘贴刷行数或拆分小提交刷次数；代码总量占比只反映本次审查范围内的相对变更规模，不等于工作强度或业务价值，两者都不参与质量评分。
- 团队评分使用的贡献权重在原始贡献权重基础上按 3%-35% 截断并重新归一化；贡献权重与代码总量占比是两个不同口径，差异必须在审查依据中说明。
- 数据缺失时退化为可用指标加权，并明确缺失字段。

### 低分尾部和附加扣分

```text
低分尾部人数 = max(1, ceil(有效参与人数 * 10%))
低分尾部得分 = 分数最低的低分尾部人数的平均分
最低人员得分 = 所有有效参与人中的最低分
```

| 团队风险事实 | 附加扣分 |
| --- | ---: |
| 存在 Blocker | 20 |
| 存在 Critical | 10 |
| 存在高风险安全漏洞 | 10 |
| 必须修复问题超过 3 个 | 5 |
| 同类问题在多人中重复出现 | 5 |
| 同一模块集中出现多个严重及以上问题 | 5 |

同一事实只应用一次最高附加扣分，不重复计算同义风险；不同事实可以累计。模块风险集中的附加扣分只针对严重及以上级别；主要及以下问题在同一模块集中出现时通过问题本身扣分和低分尾部体现，不再附加惩罚。

## 问题与报告字段

### 问题字段

| 字段 | 要求 |
| --- | --- |
| 编号 | 使用码表 `id`（如 `SEC-001`、`CMP-004`）；码表未收录的问题按其扩展规则临时定级并说明 |
| rootCauseKey | 去重合并主键，格式 `<id>:<归一化根因特征>`，必须输出 |
| locations | 全部命中位置指纹 `<文件路径>#<组件/函数名>`；同一根因多处命中合并为一条展示 |
| mergedFrom | 归一前的原始命中次数 |
| 级别和扣分 | 中文级别（阻断/严重/主要/次要/提示）与明确分值；英文枚举仅内部使用 |
| 评分维度 | 八个评分维度之一 |
| 人员和提交 | 作者、提交人、commit；当前修改使用 working tree/staged diff |
| 代码位置 | 文件、组件/函数、行号 |
| 证据 | 源码、diff、测试、构建、日志或终端证据 |
| 问题代码 | 所有已确认问题必须展示最小、脱敏、HTML 转义后的问题代码；必须修复项不得缺失代码证据 |
| 描述与影响 | 触发条件、用户影响、数据/权限/性能/维护后果 |
| 修复和复审 | 可执行修复方向（fixHint）、是否必须修复、复审命令或操作 |

### 单次审查报告顺序

1. 审查概览。
2. 提交日志。
3. 问题清单。
4. 问题详情与脱敏代码片段。
5. 问题跟踪。
6. 结论与后续动作。

### 聚合审查补充字段

- `overallScore`：短板风险校正后的团队综合得分，不得填简单平均分。
- `weightedAverageScore`：贡献权重加权平均分。
- `tailRiskScore`：最低 10% 有效参与人的平均分。
- `minPersonScore`：最低人员得分。
- `averageScore`：简单平均分，仅供参考。
- `riskCapScore`、`riskCapReasons`：团队风险封顶及原因。
- `codeTotalRatio`：每人代码总量占比，实际分析代码量归一化百分比（保留两位小数），展示于第二章。
- 每人提交数、有效变更文件数、有效变更行数、贡献权重、代码总量占比、问题数、必须修复数、计入扣分合计（递减后）和得分。
- 隐藏审查数据 JSON 的 `summary.totalScore` 与 `summary.finalRiskScore` 必须相等，且等于概览唯一展示的得分（聚合审查取团队综合得分）；原始总分、风险封顶分和封顶原因写入审查依据，不在概览另设分数字段。

### AI 编码率字段

每次审查默认按 [ai-coding-rate.md](ai-coding-rate.md) 的固定代码特征估算算法统计，记录以下字段：

- `collectedChangedLines`：采集变更代码量，等于有效新增行 + 有效删除行；排除生成文件、压缩产物、纯格式化、无业务影响的锁文件、无独立差异合并和成对回滚。
- `excludedGeneratedLines`：排除的生成代码与机械变更行数。
- `analyzedChangedLines`：实际分析代码量，等于采集变更代码量 - 排除代码量；同时作为 AI 编码率与代码总量占比的共同分母。
- `aiEstimatedLines`：折算 AI 编码量，等于各分析单元有效变更行数 × 折算系数之和，展示时取整。
- `aiCodingRate` / `manualCodingRate`：AI 编码率与人工编码率，保留两位小数；人工编码率只写入结论或说明，不在第五章按人员统计展示。
- `aiConfidence`：置信程度，只允许高、中等、低；`aiCodingMethod` 固定写“固定代码特征估算”。
- `aiCodingBasis`：中文判断依据，说明判断基线、主要命中特征、采集与排除代码量、折算结果和估算限制。
- 明确说明该指标不参与质量评分、风险封顶和门禁判定，也不作为人员绩效依据。
- HTML 审查概览展示整体 AI 编码率并在“AI 编码率说明”行写入判断依据；按人员 AI 编码率与置信程度写入第二章；第五章问题跟踪不得展示 AI 编码率和人工编码率。

## HTML 报告门禁

- 每次完成评分都必须按照 [report-generation.md](report-generation.md) 使用唯一的 `templates/CODE_REVIEW_REPORT_TEMPLATE.html` 生成 HTML 报告；不得创建其他模板，无问题或验证受阻时也不得省略。
- 问题清单编号列必须使用码表 `id`，级别列必须展示中文；问题详情必须包含 `rootCauseKey`、`locations`、`mergedFrom` 和 `fixHint`。
- 重复扫描同一范围时，`rootCauseKey` 集合必须与上次一致；不一致须在报告中说明差异原因（新代码 / 误报修正）。
- 审查概览只展示一个最终得分：单次审查使用最终总分，聚合审查使用风险校正后的团队综合得分；原始分、风险封顶和维度归属写入问题详情或结论说明，不另设主分数。
- 报告主章节必须固定为后端模板的六章名称和顺序；前端评分维度、自动化校验与未覆盖项只能写入对应章节内部。
- 所有已确认问题必须在问题详情中展示脱敏代码片段；必须修复项缺少代码证据时不得生成“已确认且必须修复”的结论。
- 自动化检查、历史基线和未覆盖项必须在审查依据或结论中说明；本 Skill 不执行浏览器验证，不得把未执行写成通过。
- AI 编码率按 [ai-coding-rate.md](ai-coding-rate.md) 的固定七项特征、固定权重和固定折算区间估算，分母为实际分析代码量（有效新增行 + 有效删除行 - 排除代码量），并标注判断基线与置信程度；不得因缺少 Git / 工具 AI 标识直接写 `0.00%`，也不得写“无法估算”。
- 报告必须在隐藏数据块 `reviewDataJson` 中嵌入合法 JSON，逐层满足 [report-generation.md](report-generation.md) 13.1 的唯一严格合同，数值与可见报告一致；未知字段、缺失字段或派生不一致时禁止输出。
- 报告生成后必须确认不存在 `{{placeholder}}` 残留，且所有来自源码、Git、终端和用户输入的动态文本均完成 HTML 转义。
- 审查正文不得直接展开到控制台或对话；报告成功生成后只输出生成状态与报告绝对路径，不得输出问题清单、评分细节、代码片段、门禁结论或验证明细。
